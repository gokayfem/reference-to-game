SIMULATION FIRST, VISUAL MOTION SECOND
Implement the conveyor graph as pure TypeScript data. Renderers interpolate candy positions along cell paths, but the graph owns which cell or machine owns each ID. A candy cannot belong to two transport nodes. Define ports as north/east/south/west and rotate directions consistently. Row coordinates increase toward screen-bottom/world +Z; world X increases by column. The JSON stores explicit ports after rotation, eliminating ambiguity in the supplied fixtures. Use cylinder arcs or a small path curve for belt turns, rather than cutting diagonally through neighboring cells.

The provided solvedLayouts and edit solutions are development fixtures. Never expose the solved layout as the initial player board. The package validator checks connectivity; the actual game still needs simulation tests for production, fairness, cooling, waiting and counting. Add a development load-solved action for test automation, disabled from the normal player UI. Use the included source/processor/goal definitions as the single data source for both simulation and explanatory UI.

Raycast against a dedicated board plane for cell selection, rather than depending on the candy mesh under the cursor. Generated art decorates the cell modules; input/output locations remain defined in code. Rebuild clean housing or port geometry locally if a fal mesh has unusable connections. Use shared procedural belt/rail geometry and animated UVs. Candy can use generated material textures with handmade star/cube meshes for precise identity. Start with inexpensive tinted material treatment and add a small number of richer transparent hero materials after performance measurement.

Create a state machine for machine visuals: idle, awaiting input, processing, blocked and completed. Its animation timing follows the simulation, never the other way around. The mixer paddle moves only while processing, presses complete one cycle per product and bin feedback fires once on delivery. Audio is subtle and event-driven, with a pooled belt loop instead of one loud loop per tile.

Suggested modules: board.ts, ports.ts, transport.ts, recipes.ts, machines.ts, editHistory.ts, levelProgress.ts, boardView.ts, candyView.ts and factoryUI.ts. A board preview scene should show one hopper, one mixer, a star press, a curve and several candies under final lighting before building the entire kit.

THREE.JS DELIVERY CONTRACT

Build a playable browser game in app/ using Three.js, TypeScript and Vite. Use a coherent installed Three.js version with its matching addons and commit the lockfile. Choose WebGLRenderer for this package's WebGL 2 target. HTML/CSS/SVG should carry crisp interface text and controls; Three.js should render the playable world. Keep simulation, rendering, input, audio, persistence and UI separate. The included JSON is proposed design data, not an existing game implementation.

Use a fixed 1/60-second simulation step, interpolation for rendering and a bounded accumulator after focus loss. Pause on document visibility changes, clear held keys on blur, and avoid simulating minutes of missed time when the tab returns. All score, goals, inventory, damage and completion displays must derive from game state. Give every pickup and entity a stable ID so events cannot apply twice. Separate visual particles from collisions and rule evaluation.

Use a right-handed, Y-up world in meters. Define forward direction and model import corrections explicitly. Normalize generated models with a wrapper transform rather than destructively guessing their orientation throughout the code. Load GLB/glTF through GLTFLoader; require compatible decoders for any compressed output. Store original generated files separately from optimized runtime assets. Record scale, pivot, attachment sockets and collider dimensions in the runtime asset manifest. Test textures and materials after import; an attractive model preview is not proof that its runtime appearance is correct.

Color management is part of art direction. Color maps use sRGB; normal and roughness data remain non-color. Avoid double output conversion. Compare the rendered palette to the reference before compensating with extra light or saturation. Dispose of resources that are replaced or unloaded. Reuse geometry and materials; instance repeated flowers, rocks, candy and scenery where appropriate. Keep transparency and post effects restrained and measure their cost.

Proposed performance target: a responsive 60 fps at 1920x1080 on a contemporary desktop, with a 30 fps floor on a documented lower-quality setting. These are targets to measure, not claims about an unbuilt game. Cap device pixel ratio initially at 1.5; expose a quality selector. Preserve palette, silhouettes and readable HUD when lowering quality; reduce shadow resolution, distant density and particles first. Start near 150 draw calls and 500k visible triangles, then change budgets only from measurements. Keep first-play downloads near 30 MB where feasible, load optional assets later, and do not ship the reference-video archive in the runtime build.

Boot to a designed title/start screen, preload essential assets with progress and a useful error state, and enter the real game on user input. Unlock audio from that gesture. Provide pause, restart, mute and volume controls. Save only appropriate progress with a versioned localStorage schema. Catch corrupted saves and recover with defaults. For first-person controls, request pointer lock only from a click, handle refusal and Escape cleanly, and allow UI interaction after unlocking. Desktop keyboard/mouse is required; touch controls are a later extension unless already straightforward.

Use app/src/core for lifecycle/input/assets/audio, app/src/game for state/rules/controllers, app/src/world for geometry/environment, app/src/ui for interface and app/src/data for level definitions. Suggested commands are npm run dev, npm run build and npm run test; document the actual scripts you implement. Include a deterministic debug scene and seed, screenshot capture points and a state inspection hook in development only. Debug shortcuts must not determine normal progression.
